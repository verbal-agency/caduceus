# Cycle handoff — G03 integrate synthetic FHIR R4 records

**Status:** complete.

## Goal boundary

G03 adds a small, deterministic, synthetic FHIR R4 fixture bundle and read-only
adapter for the declared thin-slice subset: `Patient`, `Coverage`, `Encounter`,
`Procedure`, `Condition`, `ServiceRequest`, `Claim`, and `Task`. It introduces
exact-ID retrieval, resource-type listing, reference validation, supported-subset
validation, deterministic adapter failure modes, subset documentation, and
fixture provenance. It does not add broad FHIR conformance, real EHR
integration, real PHI, payer behavior, authorization policy, or agent reasoning.

## Test-first evidence

`tests/test_synthetic_fhir_r4_adapter.py` and
`docs/fhir-r4-supported-subset.md` defined the external adapter contract before
`caduceus.adapters.fhir_r4` existed. The first test run failed during collection
with `ModuleNotFoundError`. After implementation, the first green-path run
found a deterministic failure-mode bug in the duplicate mutation path; the
adapter now copies fixture resources into a mutable list before applying
failure-mode mutations.

## Decisions and routed findings

- G03 uses a custom deterministic fixture rather than raw Synthea output because
  no generated Synthea corpus is present locally and the first adapter contract
  benefits from inspectable, stable, small records. This is recorded in fixture
  provenance and does not change the BR-01 decision to adapt Synthea later.
- The adapter validates the declared subset only. Broader FHIR package
  validation, terminology binding, FHIRPath behavior, and server search remain
  outside G03 and continue to route to B05/G12.
- Failure fixtures are generated as deterministic in-memory mutations of the
  baseline fixture, preserving the baseline JSON as the single committed normal
  case set.
- No new backlog item or roadmap reordering is required.
